ACTIVIDAD #8

Las aplicaciones web actuales dependen por completo de las bases de datos para guardar y administrar información crucial, como las contraseñas de los usuarios, bitácoras de actividad y datos financieros. Esta comunicación constante abre una brecha de seguridad importante si los datos que introduce el usuario no se revisan ni se limpian adecuadamente.

Una de las fallas más famosas y explotadas es la Inyección SQL (SQLi). Este problema ocurre cuando la aplicación mete directo los datos del usuario en las consultas SQL que ejecuta el servidor. Al hacer esto, un atacante puede manipular la consulta original para ver información confidencial, alterar datos o de plano tomar el control total del sistema. Por su gravedad, históricamente ha sido de los riesgos más críticos en el Top 10 de OWASP.

En esta práctica se documentó la explotación controlada de estas fallas usando los laboratorios de PortSwigger Web Security Academy, apoyándonos en Burp Suite como la herramienta principal para interceptar, analizar y modificar las peticiones HTTP.

1. Marco teórico: Bases de datos y SQL básico

Las bases de datos relacionales acomodan la información en tablas (con filas para los registros y columnas para los atributos) y se conectan entre sí mediante llaves primarias y foráneas. Los motores más comunes en el entorno profesional son MySQL, PostgreSQL, Oracle y SQL Server.

Comandos SQL esenciales en aplicaciones web:

  • SELECT: Se usa para traer datos de la base de datos (Ej. SELECT * FROM users;).
  • WHERE: Filtra los resultados según una condición (Ej. SELECT * FROM users WHERE username = 'admin';).
  • UNION: Junta los resultados de dos o más consultas en una sola respuesta; es un comando clave al momento de atacar.

2. ¿Cómo funciona la Inyección SQL (SQLi)?

El problema de raíz es la falta de validación. Si un sistema valida el ingreso de un usuario con una consulta vulnerable como: 

							SELECT * FROM users WHERE username = 'usuario' AND password = 'password';

Y un atacante mete en el campo de texto el código malicioso ' OR 1=1--, la consulta se rompe y se convierte en: 

							SELECT * FROM users WHERE username = '' OR 1=1--' AND password = '';

Como la condición "1 es igual a 1" siempre es verdad, el renglón del guion doble (--) descarta el resto de la consulta, dejando que el atacante se salte la autenticación sin saber la contraseña.

3. Clasificación de los ataques SQLi

Dependiendo de cómo responda el servidor y la maña que use el atacante para sacar la información, las inyecciones se dividen en:

  • In-band SQLi (En banda): El atacante ve los datos directamente en la respuesta de la página. Puede ser Union-based (agrega consultas para extraer datos de otras tablas) o Error-based (provoca errores a propósito para que el servidor escupa información de la estructura interna).
  • Blind SQLi (Ciega): La página no muestra errores ni datos directos. Aquí se usa Boolean-based (se hacen preguntas de verdadero o falso para ver cómo cambia la página) o Time-based (se meten funciones como SLEEP() para que el servidor tarde en responder y así adivinar si la condición se cumplió).
  • Out-of-band SQLi (Fuera de banda): Se usa cuando no hay respuesta visible ni cambios de tiempo. Exfiltra la información mandando peticiones a un servidor externo controlado por el atacante mediante protocolos como DNS o HTTP.

4. Impacto en la seguridad (La Tríada CIA)

Una vulnerabilidad de SQLi le pega directo a los tres pilares de la seguridad de la información:

  • Confidencialidad: Fuga de datos privados, secretos industriales o datos personales.
  • Integridad: Modificación de saldos, cambios de contraseñas o borrado de registros clave.
  • Disponibilidad: Caídas del sistema por saturación de la base de datos o pérdida total de las tablas.

5. SQLi en el Pentesting y uso de Payloads

En las auditorías de seguridad (pentesting), detectar SQLi es una de las tareas más importantes debido a su peligro. Los auditores usan herramientas como Burp Suite para cachar las peticiones del navegador, revisar qué parámetros están flojos y probar diferentes tipos de "payloads" (las líneas de código malicioso).

Estos payloads se eligen según el objetivo: saltarse el inicio de sesión, mapear las tablas existentes, o medir el tiempo de respuesta del servidor para extraer información letra por letra.

6. Principios de defensa y mitigación

Para parchar estas vulnerabilidades y programar de forma segura, se deben aplicar las siguientes buenas prácticas en el código de la aplicación:

  • Consultas parametrizadas (Prepared Statements): Es la defensa número uno; separa por completo las instrucciones SQL de los datos que mete el usuario.
  • Validación y sanitización de datos: Filtrar todo lo que mande el usuario antes de procesarlo.
  • Uso de ORM seguros: Aprovechar frameworks modernos que ya traen capas de abstracción seguras para no armar las consultas a mano.
  • Principio de mínimo privilegio: Que el usuario de la base de datos que usa la app web solo tenga permisos para lo básico y no sea administrador (root).
  • Control de errores genéricos: Configurar el sistema para que nunca muestre errores detallados de SQL en la pantalla del usuario final.

Resultados obtenidos

  • Identificación precisa de parámetros vulnerables en entornos web.
  • Explotación exitosa de laboratorios de PortSwigger usando técnicas Union y Blind.
  • Extracción segura de información y evasión de páneles de login de prueba.
  • Comprensión a fondo del flujo que siguen los datos desde el navegador hasta el motor de base de datos.

Conclusión

A través de esta práctica con los laboratorios de PortSwigger, quedó claro por qué la Inyección SQL sigue siendo un dolor de cabeza en el desarrollo web si no se toman las debidas precauciones. Dominar el uso de herramientas como Burp Suite no solo ayuda a saber cómo atacan los ciberdelincuentes, sino que nos da el conocimiento técnico necesario para blindar las aplicaciones desde la fase de desarrollo.

La seguridad no debe ser un parche de última hora; implementar consultas parametrizadas y cuidar los privilegios en las bases de datos son pasos obligatorios para proteger la integridad del negocio y los datos de los usuarios en el mundo real.
